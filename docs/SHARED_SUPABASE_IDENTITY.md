# Shared identity contract — 2026-11-19

The owner selected the existing IntMed Supabase Auth project, without a third project or billing upgrade. The website's `gerami_accounts` roles are separate from educational approval, subscriptions and entitlements. Medical records remain in the private Django database/storage. AUS remains independent. Website source: `4mirgr/gerami-website`, `backend/shared-auth/`, `server/account.mjs` and `/api/account/*`.

The website uses Google PKCE (pending the owner's Google Cloud configuration) or existing IntMed username/email/password, with provider credentials in Secure HttpOnly cookies. Only its authenticated, non-cached `/api/account/session` response is trusted by the native bridge. The bridge forwards the access cookie alone to the exact owned HTTPS URL, refuses redirects, bounds network time/payload and checks the returned UUID/role/session start. It never copies a password or refresh token. A provider outage denies access; it never falls back to a previously logged-in local manager.

`SharedIdentity` binds issuer+subject to an unusable-password Django user. Matching an existing local email returns a conflict requiring explicit verified migration; no patient record is guessed or automatically attached. New accounts have no patient link. App roles synchronize manager/secretary group membership on each request, and local inactive/staff/superuser accounts are refused by this adapter. Existing patient ownership and private-file checks still apply.

Native `PortalAccount.auth_version` revocation advances a persisted per-identity cutoff. The authoritative provider session start must be later than that cutoff; deleting a Django cookie or refreshing an old provider token does not bypass revocation. A fresh shared sign-in is required. The canonical provider session is independently checked by the website on every bridge request. In shared mode local signup/password/reset endpoints return a shared-entry response rather than creating competing credentials, and native Google account entry redirects to the shared page. The native base logout form posts to the same-origin shared logout endpoint, which checks Origin and revokes that provider session.

The owner authorizes secretary patient-panel access in shared mode, with detailed restrictions to be specified later. The explicit patient list/create/detail/edit/visit/document/upload-download routes accept manager or secretary there; physician advice approval, prescription workspace, account administration and Calendar connection remain manager-only. No secretary person has been assigned a real role by this change.

Activation remains OFF (`SHARED_AUTH_ENABLED=0`). Before enabling: deploy private Python hosting/database/storage and required privacy/restore checks, mount only native `/dash/` on the SAME main origin, remove the website CMS-only `/dash/` placeholder gate for those native routes, preserve trusted ingress/cookie headers, configure Google/email callbacks in the common Auth, deliberately link any existing accounts, and verify real HTTPS cookie/CSRF/login/logout/revocation and cross-patient isolation with synthetic data. This does not replace the public synthetic `/clinic/` export or enable clinical signup, uploads, booking or Google Calendar. No paid service or live medical operation was activated.
